Part 1

Two layers in one server

NATS is a single server binary, nats-server, that gives you two things.

  • Core NATS routes each message to whoever is subscribed at that moment. It stores nothing. If nobody is listening when a message is published, the message is gone. Delivery is at-most-once.
  • JetStream is a persistence layer built into the same server. It stores messages in streams and lets applications read them later through consumers, at their own pace, with acks and redelivery. Delivery is at-least-once. Exactly-once processing is possible by combining publish deduplication with double acks.

JetStream is switched on per server, with the -js flag or a jetstream {} block in the server config. It runs on top of core NATS: even its management API is request/reply on subjects under $JS.API.>. Everything you learn about core NATS stays true inside JetStream, so learn core NATS first.

If you know Kafka

Kafka uses one concept, the topic, for both the address of a message and the log that stores it. NATS splits these apart. That split is the main thing to unlearn.

Part 2

Core NATS entities

These are the nouns of core NATS. Everything later in this doc, JetStream included, is built from them.

EntityWhat it is
ServerThe process that accepts client connections and routes messages between them. In core NATS it keeps no messages, only a table of which connection is subscribed to what.
ConnectionOne client's long-lived TCP (or WebSocket) connection to a server. One connection can publish and subscribe at the same time.
SubjectThe address of a message, such as orders.created. Tokens separated by dots. Never created or declared.
MessageA subject, a payload of bytes, optional headers and an optional reply subject.
PublisherAny connection that sends a message to a subject.
SubscriptionA connection's registered interest in a subject pattern, optionally with a queue group name. The server delivers every matching message to it.
Queue groupA name shared by several subscriptions. Each message goes to only one member of the group.
Request/replyA pattern rather than an entity. The request carries a reply subject (an inbox such as _INBOX.k3J9), and the responder publishes its answer there.

Subjects and wildcards

A subject is a string of tokens separated by dots. It is case-sensitive. You don't create subjects: one exists as soon as somebody publishes to it or subscribes to it.

Subscriptions can use two wildcards. Published subjects can't contain them.

  • * matches exactly one token.
  • > matches one or more tokens, and only as the last token.
PatternMatchesDoes not match
orders.*orders.created
orders.dispatched		orders
orders.eu.created
orders.>orders.created
orders.eu.created		orders
orders.*.createdorders.eu.created
orders.us.created		orders.created

Subjects starting with $ are used by the system: $JS. for JetStream, $KV. for the key-value store, $SYS. for server events. Reply inboxes start with _INBOX. by convention. Keep your own subjects away from these prefixes.

Gotcha

The hierarchy has to be consistent. orders.* does not match order.created, because the first token is order, not orders. Put the most general token first, so that one subscriber can take orders.> and another only orders.*.created.

Messages, seen on the wire

A message has a subject, a payload (up to 1 MB by default, set by max_payload), optional headers and an optional reply subject. The client protocol is plain text, which makes the core model easy to see:

# subscriber's connection → server
SUB orders.* billing 7           subject, queue group, subscription id

# publisher's connection → server
PUB orders.created 11            subject, payload size in bytes
{"id":1001}

# server → subscriber's connection
MSG orders.created 7 11          subject, subscription id, size
{"id":1001}

There is no queue in this exchange. billing is just an argument on SUB. Hold on to that; it explains Part 4.

Subscriptions and queue groups

When several plain subscriptions match a subject, each one gets its own copy of every message. This is fan-out.

When several subscriptions share a queue group name, each message goes to just one of them. This is load balancing. Queue groups need no setup: a group exists while it has members. To scale up, start another process with the same queue name.

You can mix both on one subject. Each queue group counts as one receiver, alongside every plain subscription.

nc, _ := nats.Connect(nats.DefaultURL)

nc.Subscribe("orders.*", logHandler)                    // gets every message
nc.QueueSubscribe("orders.*", "billing", billHandler)   // one "billing" member per message

Question

What do subscribers subscribe to: queues or subjects?

Subjects. Core NATS has no queue object you can subscribe to. A queue group is an optional name you attach to a subscription on a subject. Subscriptions on the same subject with the same queue name share the messages; subscriptions without a queue name each get a copy.

Request/reply

Request/reply is RPC built from pub/sub. The requester creates a unique inbox subject, subscribes to it, and publishes the request with that inbox as its reply subject. The responder publishes the answer to the inbox. Responders in a queue group become a load-balanced service.

// responder: run as many as you like
nc.QueueSubscribe("orders.lookup", "order-svc", func(m *nats.Msg) {
    m.Respond([]byte(`{"status":"dispatched"}`))
})

// requester
resp, err := nc.Request("orders.lookup", []byte(`{"id":1001}`), 2*time.Second)

If nobody is subscribed to orders.lookup, the server answers at once with a "no responders" status (nats.ErrNoResponders in Go) instead of letting the request time out.

What core NATS promises, and what it doesn't

  • At-most-once. No storage, no acks, no redelivery.
  • Nobody listening means the message is dropped. A subscriber that is offline for one second misses everything published in that second.
  • Order per publisher. Messages from one publisher reach each subscriber in the order they were published. There is no ordering across different publishers.
  • Publishers are never slowed down by subscribers. A subscriber that can't keep up gets disconnected instead. Part 4 shows why.

Part 3

Worked example: an orders system

An order service publishes two events. Two teams consume them: billing runs three instances, analytics runs two. An audit logger wants every message.

// order service
nc.Publish("orders.created", data)
nc.Publish("orders.dispatched", data)

// billing: run 3 processes
nc.QueueSubscribe("orders.*", "billing", handle)

// analytics: run 2 processes
nc.QueueSubscribe("orders.*", "analytics", handle)

// audit log: a plain subscription
nc.Subscribe("orders.>", audit)

When orders.created is published:

SubscriberGets the message?
billing (3 instances)Yes, exactly one of the three instances
analytics (2 instances)Yes, exactly one of the two instances
audit (plain)Yes

That is three deliveries for one publish. Inside a handler, msg.Subject tells you which event arrived.

Question

We can have subjects orders.created and orders.dispatched and publish to them, right? Can a set of workers listen to orders.*? What about two subscriber groups on orders.*?

Yes to all three. Subjects need no setup, so you just publish. One queue group on orders.* gives you a pool of workers that share the load. Two queue groups with different names on orders.* each get every message, and inside each group one member handles it.

This design has one weakness. If all three billing instances are down when an order is created, billing never sees that order. Nothing stored it, and nothing will retry it. Keep that in mind; it is the reason JetStream exists (Part 5).

Part 4

Inside the server: how fan-out works

Question

How is this fan-out handled inside NATS? It seems there must be a queue for "billing" and one for "analytics". And when an event reaches the servers, do they duplicate the message?

There is no queue for either group, and nothing is stored. The server keeps a table of subscriptions. When a message arrives, it looks up the matching subscriptions, picks one member of each queue group, and writes the bytes into the outbound buffer of each chosen connection. That write, once per recipient, is the only duplication.

The interest table

Each server keeps a subject-token tree of subscriptions, called the sublist. For our example it holds:

orders.*  →  queue billing:    [conn 11, conn 12, conn 13]
             queue analytics:  [conn 21, conn 22]
orders.>  →  plain:            [conn 31]

Subscribing adds an entry. Unsubscribing or disconnecting removes it. Lookups for a literal subject are cached, so repeated subjects are cheap. That table is the whole state of core NATS.

One publish, step by step

  1. The server reads PUB orders.created.
  2. It matches the subject against the table. Both orders.* and orders.> match, which gives one plain subscription and two queue groups.
  3. It picks one member of each queue group at random. In a cluster it prefers members connected to itself.
  4. It appends the message to the outbound buffer of each chosen connection, and a writer flushes each buffer to its socket.

The only buffer is per connection

Each connection has an outbound buffer, and that is the closest thing to a queue in core NATS. If a subscriber reads too slowly, its buffer grows. Once it passes a limit (max_pending, 64 MB by default), the server marks it a slow consumer and closes the connection. The publisher is never made to wait. Client libraries also keep a pending limit per subscription and drop messages, with a slow-consumer error, when it fills.

In a cluster

  • Servers share their interest tables with each other over routes.
  • A message crosses a route at most once per remote server, however many subscribers live there. The remote server then does its own local fan-out.
  • For queue groups, the origin server prefers a local member. If it has none, it forwards the message to a server that has members, tagged with the queue groups it is meant for, and that server picks the member.

Part 5

From core NATS to JetStream

Part 3 ended with a gap: a group that is offline misses messages, and a failed handler never gets a retry. JetStream closes that gap by storing messages and tracking who has processed them.

Core NATSJetStream
StorageNoneMessages kept in a stream, on disk or in memory
DeliveryAt-most-onceAt-least-once; exactly-once with dedup and double acks
Acks and retriesNonePer message; unacked messages are redelivered
ReplayImpossibleFrom any sequence number or time
Offline groupsMiss messagesCatch up when they return
Flow controlSlow subscribers get disconnectedClients pull at their own rate; capped by MaxAckPending
Your app attaches toA subject, through a subscriptionA consumer, which belongs to a stream

The shift to make

In core NATS, an application subscribes to subjects. In JetStream, a stream captures subjects and stores the messages, and an application reads through a consumer on that stream. Subjects still decide what a stream stores and which stored messages a consumer visits. They are no longer what your application attaches to.

JetStream entities

EntityWhat it is
StreamA stored, ordered log of messages. It captures every message published to its subjects, numbers them, and keeps them according to its retention policy. Belongs to one account.
Stream sequenceA message's position in the stream: 1, 2, 3 and so on. Never reused. Every consumer sees the same sequence for the same message.
ConsumerServer-side state attached to exactly one stream: a filter, a starting point, a position, and ack bookkeeping. A view or cursor over the stream. Applications read through it.
AckThe application's confirmation that a delivered message was processed. Until it arrives, the message counts as pending and can be redelivered.
PubAckThe server's confirmation to a publisher that a message was stored, with the stream name and sequence number.
Key-value storeA bucket of keys with history and watch, implemented as a stream.
Object storeLarge files split into chunks, implemented as a stream.

Part 6

Streams

A stream is created explicitly, with a name and the list of subjects it captures. From then on, every message published to one of those subjects is stored, whoever publishes it.

js, _ := jetstream.New(nc)

stream, _ := js.CreateStream(ctx, jetstream.StreamConfig{
    Name:      "ORDERS",
    Subjects:  []string{"orders.>"},     // what this stream captures
    Storage:   jetstream.FileStorage,    // or MemoryStorage
    Replicas:  3,                        // copies across a cluster, 1 to 5
    Retention: jetstream.LimitsPolicy,   // the default
    MaxAge:    7 * 24 * time.Hour,
})

Publishing into a stream

Publishers still publish to subjects. A plain core nc.Publish("orders.created", …) gets stored too, but the publisher has no way to know whether it was. js.Publish waits for the PubAck:

ack, err := js.Publish(ctx, "orders.created", data)
// ack.Stream == "ORDERS", ack.Sequence == 42

// deduplication: same ID inside the stream's Duplicates window (2 minutes by default) is stored once
ack, err = js.Publish(ctx, "orders.created", data, jetstream.WithMsgID("order-1001-created"))
// a repeat returns ack.Duplicate == true

Retention: when messages leave a stream

PolicyA message is removed whenTypical use
Limits (default)A limit is reached: MaxAge, MaxBytes, MaxMsgs or MaxMsgsPerSubjectEvent log with replay and several independent readers
InterestEvery consumer whose filter matches it has acked it, or a limit is reachedFan-out where storage should shrink as readers finish
WorkQueueOne consumer acks it, or a limit is reachedA job queue: each message processed once

When a stream hits a limit, its discard policy decides what happens: DiscardOld (the default) deletes the oldest messages, DiscardNew rejects new publishes.

A subject belongs to one stream

Within an account, a subject can be captured by only one stream. Creating a stream whose subjects overlap an existing stream's subjects fails with subjects overlap with an existing stream. So a published message always lands in exactly one stream, or in none.

Question

Say I have three subjects, orders.A, orders.B and orders.C. I could create 2³ streams from their combinations. Does a message on orders.A get duplicated into every stream that includes it?

No, because JetStream won't let you create those streams. Once one stream has orders.A, no other stream can take orders.A, orders.* or orders.>. Your only options are splits where no subject appears twice: one stream on orders.>, three streams with one subject each, or {orders.A, orders.B} plus {orders.C}. Either way, a message on orders.A is stored in exactly one stream.

Copying between streams: mirrors and sources

If you do want the same message in several streams, you ask for the copy explicitly. Both of these store real copies.

  • Mirror: a read-only copy of exactly one other stream. It has no subjects of its own. Used for backups or a read replica in another region.
  • Sources: a stream that pulls in messages from one or more other streams, optionally filtered by subject, and may also capture subjects of its own. Used to aggregate, for example regional streams into a global one.

Built on streams: key-value and object stores

A key-value bucket named profiles is a stream named KV_profiles that captures $KV.profiles.>. A put is a publish to $KV.profiles.<key>. A get reads the last message on that subject. History is MaxMsgsPerSubject, and a watch is a consumer. The revision of a key is the stream sequence of the message that set it.

kv, _ := js.CreateKeyValue(ctx, jetstream.KeyValueConfig{Bucket: "profiles", History: 5})
kv.Put(ctx, "user.42", []byte(`{"plan":"pro"}`))
entry, _ := kv.Get(ctx, "user.42")   // entry.Revision() is a stream sequence

An object store bucket named assets is a stream named OBJ_assets holding chunk messages plus one metadata message per object.

Part 7

Consumers

Definition

A consumer is a server-side object attached to exactly one stream. It holds:

  • a filter: which of the stream's subjects it visits (optional);
  • a starting point: its DeliverPolicy;
  • a position: the next stream sequence to deliver;
  • an ack state: which delivered messages still wait for an ack, and how many times each was delivered.

It is a view or cursor over the stream. It is not a subscription, and it is not a subject. It lives on the server whether or not any application is connected to it.

Creating billing and analytics

billing, _ := stream.CreateOrUpdateConsumer(ctx, jetstream.ConsumerConfig{
    Durable:       "billing",
    FilterSubject: "orders.created",
    AckPolicy:     jetstream.AckExplicitPolicy,
})

analytics, _ := stream.CreateOrUpdateConsumer(ctx, jetstream.ConsumerConfig{
    Durable:       "analytics",
    FilterSubject: "orders.>",     // or leave it out: the stream already covers orders.>
    AckPolicy:     jetstream.AckExplicitPolicy,
})

A filter must fall inside the stream's subjects, so payments.> would be rejected on this stream. From server 2.10, FilterSubjects takes several filters at once.

How an application reads from a consumer

// run this in each billing instance; all three share the "billing" consumer
cc, _ := billing.Consume(func(msg jetstream.Msg) {
    process(msg.Subject(), msg.Data())   // Subject() is still "orders.created"
    msg.Ack()
})
defer cc.Stop()

Consume hides the mechanics. Underneath, a pull consumer works like this, all on core NATS subjects:

  1. The client subscribes to its own inbox, such as _INBOX.k3J9.
  2. It publishes a pull request to $JS.API.CONSUMER.MSG.NEXT.ORDERS.billing, with the inbox as reply subject and a body like {"batch":10,"expires":30000000000}.
  3. The server sends up to 10 messages to the inbox. Each keeps its original subject (orders.created) and carries a reply subject like $JS.ACK.ORDERS.billing.…, which encodes the delivery count and the stream and consumer sequences.
  4. msg.Ack() publishes to that ack subject. The consumer updates its ack state.

A push consumer has a DeliverSubject in its config instead. The server publishes messages to that subject as they become available, and the client reads them with an ordinary core subscription. Setting DeliverGroup makes it a queue group on the deliver subject. Push consumers are the older style. Pull consumers are recommended for new code because the client controls how much it takes.

Question

In JetStream, are subscribers still subscribing to subjects, or to streams?

Neither, strictly. An application reads from a consumer, and the consumer belongs to a stream. Subjects still matter in two places: the stream's subject list decides what gets stored, and the consumer's filter decides which stored messages it visits. Messages do still travel to your application over subjects, but those are an inbox or deliver subject owned by the consumer, not orders.created.

One trap: the older Go API has js.Subscribe("orders.*", …), which looks like a subject subscription. Behind the scenes it finds the stream that captures orders.* and creates a consumer on it for you.

Durable and ephemeral consumers

DurableEphemeral
Created withDurable: "billing"No Durable (the server picks a name, or you set Name only)
Survives restartsYes. It resumes from its saved position.No. Deleted after InactiveThreshold with no client attached (5 seconds by default)

"Durable" describes the consumer, not the stream. The stream's messages are stored either way. An ordered consumer is a client-library convenience on top of an ephemeral one: no acks, strict order, and it recreates itself if it spots a gap. Use it for replaying a stream in order (js.OrderedConsumer in Go).

Question

In the example, is either "analytics" or "billing" called a durable?

Both. Setting Durable: "billing" and Durable: "analytics" is what makes them durable consumers. The server keeps their position and ack state, so when billing restarts it continues where it left off.

Where a new consumer starts

DeliverPolicyStarts at
DeliverAll (default)The oldest message still in the stream
DeliverNewOnly messages stored after the consumer is created
DeliverLastThe last message in the stream
DeliverLastPerSubjectThe latest message for each subject, useful for "current state"
DeliverByStartSequenceA given sequence (OptStartSeq)
DeliverByStartTimeA given time (OptStartTime)

The policy only applies when a consumer is created. A durable consumer uses it once; after that it resumes from its saved position.

Question

If a new ephemeral consumer connects, does it read from the very first message in the stream, or from the newest message onwards?

It depends on DeliverPolicy. The default, DeliverAll, starts at the oldest message the stream still holds, which is not necessarily sequence 1 if retention already removed older messages. Use DeliverNew to see only new messages. An ephemeral consumer is new every time, so its policy applies every time.

Acks, redelivery and back-pressure

CallMeaning
msg.Ack()Done. It won't be delivered again.
msg.Nak()Failed. Redeliver it now, or later with NakWithDelay.
msg.InProgress()Still working. Restart the ack timer.
msg.Term()Never redeliver this message.
msg.DoubleAck(ctx)Ack and wait for the server to confirm it. Used for exactly-once processing.
  • AckWait (30 seconds by default): a delivered message with no ack after this long is redelivered.
  • MaxDeliver (unlimited by default): how many delivery attempts before the consumer gives up on a message. BackOff sets a schedule for redeliveries.
  • MaxAckPending (1,000 by default): when this many messages are delivered but not acked, the consumer stops handing out more. This is JetStream's back-pressure.

Fan-out and work sharing in JetStream

The two patterns from core NATS map onto consumers:

  • Fan-out: one consumer per group. Billing and analytics each get every message their filter matches.
  • Work sharing: several instances pull from the same consumer. Each message goes to one instance at a time, like a queue group. Instances process in parallel, so processing order across them isn't guaranteed. If order matters, use one instance or MaxAckPending: 1.

Question

Can the consumer "billing" look only at orders.created while "analytics" looks at orders.>?

Yes. Each consumer has its own filter: FilterSubject: "orders.created" for billing and "orders.>" (or none) for analytics. Billing's cursor skips anything that isn't orders.created; analytics sees everything.

Watch the retention policy, because these filters overlap. Limits and Interest are fine. A WorkQueue stream rejects this setup, since work-queue streams don't allow consumers with overlapping filters.

Question

But the underlying stream is the same for both, right?

Yes. Both consumers sit on the same ORDERS stream, which holds one copy of each message. They are two cursors over it, each with its own filter, position and acks. RabbitMQ is the opposite: there every bound queue gets its own copy.

Part 9

Security and accounts

NATS is multi-tenant. Three entities form the hierarchy, from the top down:

EntityWhat it is
OperatorThe root of trust in the JWT model. It signs account JWTs, and servers are configured to trust it.
AccountAn isolated subject namespace. Two accounts can both use orders.created without seeing each other's messages. Streams, consumers and JetStream limits belong to an account.
UserA credential inside one account, with allow and deny rules for the subjects it may publish and subscribe to.

Authentication can be simple, with users, passwords, tokens or NKeys written into the server config. Or it can be decentralized: operator, account and user JWTs signed with NKeys (Ed25519 keys), managed with the nsc tool, so accounts and users can be added without restarting servers. Every connection type can use TLS. A system account, $SYS, carries server events and monitoring.

Sharing between accounts: exports and imports

Accounts see nothing of each other unless one exports subjects and another imports them. There are two kinds:

  • Stream export/import: a one-way flow of messages. The orders account exports orders.>, and the analytics account imports it.
  • Service export/import: request/reply. The importing account can send requests to the exporter's service and get replies back.

Gotcha

"Stream" in exports and imports means a flow of messages between accounts. It has nothing to do with a JetStream stream.

Part 10

The model in six lines

  1. Applications exchange messages addressed by subjects.
  2. Core NATS routes each message to the subscriptions that match it at that moment, then forgets it.
  3. A queue group makes a set of subscriptions share messages: one member per group gets each one.
  4. A stream captures subjects and stores each message once, in order, with a sequence number.
  5. A consumer is a cursor over one stream. Applications read and ack through it, and many consumers can share one stream.
  6. Routes, gateways and leaf nodes connect servers; accounts keep tenants apart.
