1Two stores, one protocol

Redis keeps its whole dataset in RAM. Apache Kvrocks implements the Redis protocol, the format Redis clients use to send commands and read replies. An application that uses a Redis client library can point it at Kvrocks and keep sending the same commands, with no code changes. Underneath, Kvrocks stores data on disk in RocksDB and uses RAM only as a cache. Most differences in this tutorial come from that one design choice.

Some commands are missing or behave differently, so check the supported-commands list for the ones your application uses.

Redis suits hot, latency-critical data that fits in memory, such as caches, sessions, rate limiters and leaderboards. Kvrocks suits large datasets where you want the Redis API without paying for all that RAM and can accept a little more latency.

What "single-threaded" means in Redis

Redis runs its own event loop, a small library called ae on top of epoll or kqueue. One thread waits for sockets to become ready, reads requests, runs commands and writes replies. It is the same reactor model as Python's asyncio, and it lets one thread serve thousands of connections.

The difference from asyncio is that a Redis command never pauses partway through. An asyncio coroutine can yield at any await. A Redis command runs to completion before the next one starts. That makes every command atomic without locks. It also means one slow command, such as KEYS * or a heavy Lua script, blocks every client.

Some work does run outside the main thread:

  • I/O threads (Redis 6.0+) read and parse requests and write replies. Commands still execute on the main thread.
  • Background threads free large values (UNLINK), run fsync for the AOF, and close files.
  • Forked child processes write RDB snapshots and rewrite the AOF.

Why this matters for persistence

Snapshots and log rewrites happen in a forked child, so saving to disk doesn't stall the event loop. The price is the fork itself. On a large dataset it can cause a short pause and use extra memory while the child runs.

2Crashes, faults and failures

"Crash" covers three different events, and each one erases a different amount of state. Say which one you mean whenever durability comes up.

What each crash erases depends on two system calls that servers use to save data:

  • write() copies bytes from the program's memory into the OS page cache, a buffer in the kernel's memory, and usually returns quickly. The kernel writes cached bytes to disk later, on its own schedule. Once write() returns, the kernel holds those bytes, independent of the program.
  • fsync() tells the kernel to send a file's cached bytes to the disk now. It returns only after the disk confirms they are stored, which is why it is slow.

Process crash

Examples
Segfault, OOM kill, kill -9, container restart
Survives
Anything already handed to the OS. The OS keeps running and still writes it to disk.
Lost
Data that existed only in the process's own memory.

Machine crash

Examples
Power loss, kernel panic, VM or host failure
Survives
Only data already forced to disk with fsync.
Lost
The OS's memory buffer too, so data written but not yet synced is gone.

Disk loss

Examples
A dead disk, a cloud instance whose local storage is wiped
Survives
Only copies on another machine, from replication or backups.
Lost
Everything on that disk, including data that was synced.

Faults and failures

Each of these crashes is a fault. Dependability engineering describes what can follow as a chain of three steps.

Fault

The underlying cause.

A process crash, a machine crash, a dead disk.

→

Error

The wrong internal state the fault leaves behind.

A restarted node missing a write it acknowledged.

→

Failure

A client visibly gets wrong service.

A write the client saw succeed is gone.

Fault tolerance stops the chain before it reaches a failure. In this tutorial that means logs, fsync and replication. Every durability setting from here on decides which faults a store tolerates and which ones become failures. One unhandled fault is enough to cause a failure.

The words depend on the level you look from

One component's failure is a fault for the system that contains it. A dead disk is a failure from the disk's point of view and a fault from the database's. If a replica takes over, the database has no failure. If nothing takes over and data is lost, the database itself has failed.

Where a write can live

On its way to safety, a write passes through up to four places. Each step takes more time and tolerates more faults. Every durability setting in this tutorial is really a choice about how far down this ladder a write gets before the client hears OK.

3How Redis persists

Redis data lives in RAM, place 1 on the ladder. Two optional mechanisms copy it further down: RDB snapshots and the AOF log. You can use either, both or neither.

RDB: periodic snapshots

  • Writes the whole dataset to a compact binary file. It runs on a schedule, such as save 300 100 (every 5 minutes if at least 100 keys changed), or on demand with SAVE or BGSAVE.
  • A forked child writes the file, so the main thread keeps serving clients.
  • Strengths: small files, fast restarts, easy backups and copies.
  • Weakness: any fault, even a process crash, loses every write since the last snapshot.

AOF: a log of every write

  • Appends each write command (SET, INCR and so on) to a file. On restart, Redis replays the file to rebuild the data.
  • Redis hands each log entry to the OS before sending the reply, so an acknowledged write has reached place 2. The appendfsync setting controls how soon it reaches place 3.
appendfsyncWhen Redis calls fsyncLost in a machine crashSpeed
always Before replying to each write ✓ Nothing Slowest
everysecdefault Once per second, in a background thread ! About the last second Fast
no Never; the OS flushes on its own schedule ✕ Up to about 30 s on default Linux settings Fastest
  • The log grows forever, so Redis periodically rewrites it into the shortest set of commands that recreates the current state. A forked child does this too.
  • Strength: much better durability than snapshots alone. Weakness: bigger files and slower restarts.

Defaults and combinations

  • Out of the box, Redis has RDB snapshots on and AOF off.
  • You can enable both. Since Redis 4, an AOF rewrite can start the file with an RDB snapshot and append commands after it (aof-use-rdb-preamble). Restarts stay fast, and a crash loses at most about a second.
  • For a pure cache, people often turn both off.

4How Kvrocks persists

Kvrocks has no RDB or AOF. Its data already lives on disk in RocksDB, and RocksDB protects recent writes with a write-ahead log (WAL). Like the AOF in Redis, the WAL is the fault tolerance that keeps a process crash from becoming a failure.

  • Each write is appended to the WAL and handed to the OS before Kvrocks replies, which puts it in place 2. A process crash loses nothing that was acknowledged.
  • By default Kvrocks doesn't wait for fsync. A machine crash can lose recent writes still sitting in the OS page cache.
  • Setting rocksdb.write_options.sync yes makes every write wait for fsync, which puts it in place 3, at a cost in throughput.
  • Restarts are fast because the data is already on disk. Redis has to load its whole dataset into RAM before it can serve.

Matching settings

Kvrocks defaults are closest to Redis with appendfsync no. A process crash is safe, and the OS decides when the log reaches disk. Kvrocks with sync yes matches Redis with appendfsync always.

The biggest difference is the default. Out of the box, Kvrocks tolerates a process crash that would cost a default Redis every write since its last snapshot. Once both use the same fsync policy, they protect a single machine about equally well. Kvrocks still restarts faster, because it doesn't have to load the dataset into RAM.

6Failures fsync can't prevent

Everything above concerns faults on one machine. Surviving disk loss needs place 4, a copy on another machine. Both stores get there with asynchronous replication: the primary replies OK first and sends the write to replicas afterward.

  1. t0The client sends SET order:42 paid to the primary.
  2. t1The primary applies it and replies OK. The client now treats the write as done.
  3. WindowThe write exists only on the primary. If the primary dies now and a replica is promoted, the write is gone, even though the client saw OK. The primary's crash is the fault, and the missing write is the failure.
  4. t2The replica receives the write. From here on, a failover keeps it.
  • Failover. When a replica is promoted, acknowledged writes it hadn't received are lost. Both stores have this gap. In Redis, WAIT numreplicas timeout makes a client block until that many replicas confirm a write, which narrows the gap without fully closing it.
  • Network partition. A primary cut off from the rest of the cluster can keep accepting writes for a short time. Those writes are discarded when it rejoins. How long this lasts depends on the failover manager: Sentinel or Redis Cluster for Redis, kvrocks-controller for Kvrocks.
  • Memory full. Eviction isn't a fault. Redis is working as configured, and clients still lose data. With maxmemory and a policy like allkeys-lru, Redis deletes keys to make room. Kvrocks doesn't evict, since RAM is only its cache. When it reaches its disk limit (max-db-size), new writes fail instead.

Rule of thumb

Use either store for data you can rebuild or can afford to lose a little of, such as caches, sessions, counters and queues with retries. Keep the source of truth in a database built for durability. If you need Redis-style access with strong durability, look at a service such as AWS MemoryDB, which writes each change to a replicated transaction log before acknowledging it.

7Takeaways

  • Ask two questions. Where is the write when the client hears OK, and which faults erase that place?
  • Separate faults from failures. Crashes are faults, and they will happen. A failure is a client seeing lost or wrong data. Every setting in this tutorial decides which faults become failures.
  • Name the fault. A process crash, a machine crash and disk loss each erase a different amount. write() protects against the first, fsync() against the second, and only another machine against the third.
  • Defaults differ most. Default Redis loses every write since the last snapshot, even in a process crash. Default Kvrocks loses nothing in a process crash.
  • Matched settings land in the same place. With the same fsync policy, both stores protect one machine about equally well. Kvrocks restarts faster.
  • Replication is asynchronous in both. A failover can lose writes that clients saw succeed. Keep the source of truth in a database built for durability.

8Check yourself

Try each one before opening the answer.

A Redis server with default settings is killed by the OOM killer. What is lost?

Every write since the last RDB snapshot. The default has AOF off, so recent writes existed only in Redis's memory, and a process crash is enough to lose them.

A Kvrocks server with default settings gets kill -9. Later, a different Kvrocks machine loses power. What does each lose?

The killed process loses nothing it acknowledged, because the WAL entries were already handed to the OS. The power loss can lose recent writes the OS hadn't flushed to disk, unless rocksdb.write_options.sync is yes.

A single Redis node runs with appendfsync always and no replicas. Its disk dies. What survives?

Nothing from that machine. fsync protects against a machine crash, but not against losing the disk itself. Only a replica or a backup on another machine would survive.

A primary dies, and a replica that had received every acknowledged write is promoted. Did the fault cause a failure?

Not a data-loss failure. Every write a client saw succeed is still there, so replication tolerated the fault. Clients can still get errors during the seconds the failover takes, which is a short availability failure. From the primary node's own point of view, it simply failed.
